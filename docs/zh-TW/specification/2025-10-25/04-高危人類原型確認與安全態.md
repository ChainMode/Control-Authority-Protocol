# 第 4 章：高危人類原型確認與安全態

## 4.1 參數綁定的顯式人類原型確認門（`HumanConfirmationProof`）

對於所有 `effective_criticality` 為 **`high`** 或 **`critical`** 的操作（**即使當前會話已處於最高信任等級 `G1`**），CAP 評估器 **MUST** 強制校驗隨請求提交的 `human_confirmation`（`HumanConfirmationProof`），絕不允許以「自動化便利」或「歷史表現良好」為由免除逐次確認：

1. **規範身分校驗**：`human_confirmation.human_prime_id` **MUST** 符合規範化人類原型識別碼正規表示式 `^hid_[a-z2-7]{16,}$`。
2. **時效新鮮度校驗**：`human_confirmation.expires_at_epoch_ms` **MUST** 嚴格大於當前評估時間戳記 `req.now_epoch_ms`。
3. **宿主可信揭露證明**：`human_confirmation.terminal_attested_disclosure` **MUST** 為 `true`，表明由宿主可信互動介面（而非 `Fay` 自報文字）向人類原型完整展示了目標資源、操作及不可逆風險。
4. **參數規範化 SHA-256 綁定**：計算本次請求 `req.params` 按字典序鍵排序規範化 JSON（見 §3.1）的 UTF-8 位元組序列的 SHA-256 小寫十六進位摘要（64 字元），`human_confirmation.confirmed_params_sha256` **MUST** 與該摘要逐字元完全相等。

若 `human_confirmation` 缺失，或上述四項條件中任一項不成立（例如確認後請求參數中的 `latch_id` 被竄改），評估器 **MUST** 立即回傳 `decision = "DENY"`、`error_code = "E_CONFIRMATION_REQUIRED"` 與 `diagnostic_code = 2006`。

## 4.2 `G0` 人類原型緊急接管與零阻塞安全態指令

人類原型在任何時刻均享有對宿主的絕對優先接管權。當請求中攜帶 `g0_override == true` 或 `grant.mandate_binding.session_grade == "G0"` 時：

1. **立即搶佔拒絕**：CAP 評估器 **MUST** 在 Mandate 過期/模式校驗之前立即攔截 `Fay` 的控制請求，回傳 `decision = "DENY"`、`error_code = "E_G0_EMERGENCY_OVERRIDE"` 與 `diagnostic_code = 2003`。
2. **確定性安全態指令（`G0SafeStateDirective`）**：
   - 若目標 `ResourceCapabilityDescriptor.safe_states` 非空，評估器 **MUST** 選擇首選安全態 `safe_states[0].safe_state_id`，在裁決中輸出：
     `{ "action": "enter_safe_state", "safe_state_id": "<safe_states[0].safe_state_id>", "blocks_human_takeover": false }`；
   - 若目標資源未宣告 `safe_states`（或清單為空），評估器 **MUST** 輸出：
     `{ "action": "terminate_and_alert", "blocks_human_takeover": false }`，指令宿主立即終止在途受控動作並向人類原型發出顯式告警。
3. **零阻塞不變量**：在任何情況下，`safe_state_directive.blocks_human_takeover` **MUST** 恆為布林常數 `false`。宿主的任何安全態過渡或清理流程 **SHALL NOT** 阻塞、鎖定或延遲人類原型直接奪回實體或互動控制權。

## 4.3 規範錯誤碼與數值診斷伴隨碼表

CAP 1.0 線格式採用穩定的大寫底線字串作為規範錯誤碼（`CapErrorCode`），並在測試向量與診斷日誌中綁定一一對應的數值診斷碼（`2001`–`2099`）：

| 規範錯誤碼 (`error_code`) | 數值診斷碼 (`diagnostic_code`) | 觸發階段與規範語意 |
|--------------------------|-------------------------------|-------------------|
| `E_WEAK_MANDATE_BINDING` | `2001` | `high`/`critical` 未使用 `model_a_plus_b`（或缺少派生證明/線上新鮮度），或 `sensitive` 使用了離線快取 `model_c_offline_cache` |
| `E_GRADE_INSUFFICIENT` | `2002` | 會話等級低於 `grant.min_grade`，或不滿足 `FayingGrade × AccessMode × Criticality` 矩陣 |
| `E_G0_EMERGENCY_OVERRIDE` | `2003` | 人類原型觸發 `G0` 緊急接管，拒絕 `Fay` 控制並輸出非阻塞 `safe_state_directive` |
| `E_UNKNOWN_OPERATION` | `2004` | 請求的 `resource_id` 或 `operation_id` 未在已驗簽 `DriverCapabilityManifest` 中宣告 |
| `E_UNTRUSTED_MANIFEST` | `2005` | `DriverCapabilityManifest` 缺失簽章、信任錨不存在或 Ed25519 驗簽失敗 |
| `E_CONFIRMATION_REQUIRED` | `2006` | `high`/`critical` 操作缺失有效、未過期、終端證明揭露且參數 SHA-256 相符的 `HumanConfirmationProof` |
| `E_OUT_OF_SCOPE_FUND_TRANSFER` | `2007` | 請求或操作宣告 `domain_category == "fund_transfer"`，超出 CAP 1.0 協定邊界 |
| `E_MANDATE_INVALID` | `2008` | Mandate 已撤銷、已過期、線上模型下 `online_fresh == false`，或主體/資源/模式不相符 |
| `E_PROTOCOL_VERSION_UNSUPPORTED` | `2098` | `protocol_version` 不等於受支援的兩段式版本 `"1.0"` |
| `E_PROTOCOL` | `2099` | 協定封包結構異常或兜底錯誤；歷史別名 `E_INVALID_MESSAGE` 在輸入正規化時 **MUST** 映射為 `E_PROTOCOL` |

## 4.4 實作符合性（Conformance）判據

任一終端、驅動宿主或執行時實作若宣告符合 **CAP 1.0（`2025-10-25` 版次）**，**MUST** 同時滿足以下全部可驗證條件：

1. 完整實作第 0–4 章定義的預設拒絕 8 步評估管線、單調危重度地板、三維分級矩陣、參數 SHA-256 人類原型確認門及 `G0` 非阻塞安全態指令；
2. 輸入輸出結構嚴格符合 `schemas/cap-1.0.cddl` 與 `schemas/cap-1.0.json`；
3. 載入並執行官方規範性語意測試向量集 `vectors/semantic/d1-d7-conformance.json` 中的全部 14 條測試向量（`V01`–`V14`），所有裁決結果、有效危重度、防降級夾緊旗標、錯誤碼、診斷碼與安全態指令與預期值 **100% 一致**。
