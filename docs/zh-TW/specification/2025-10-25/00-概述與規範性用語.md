# 第 0 章：概述與規範性用語

## 0.1 協定使命與範圍

**控制權限協定（Control Authority Protocol，CAP）** 是位於數位化身（`Fay`，含個人數位化身 `iFay` 與公共數位化身 `coFay`）與宿主（`Host`，即被附身控制的硬體終端設備或用戶端應用程式）之間的預設拒絕（Default-Deny）控制權門控協定。CAP 將上游授權委任轉化為針對具體宿主資源與驅動操作的確定性准入裁決，確保任何不可逆物理動作或關鍵系統變更在執行前受到密碼學能力底線與人類原型（`Human Prime`）意願的嚴格約束。

CAP 1.0 的規範範圍涵蓋：

1. 控制權評估請求（`CapEvaluationRequest`）與確定性裁決輸出（`CapDecision`）的資料模型與線格式；
2. 經密碼學簽章的驅動能力清單（`DriverCapabilityManifest`）驗簽、危重度底線與不可逆後果地板計算；
3. 對上游 `Faying-Protocol` 委任證據（`MandateEvidence`）的線上新鮮度與會話派生綁定核驗；
4. `FayingGrade × AccessMode × Criticality` 三維分級准入矩陣；
5. 高危與致命操作的參數雜湊綁定人類原型顯式確認門（`HumanConfirmationProof`）；
6. 人類原型 `G0` 緊急接管搶佔與非阻塞安全態指令（`G0SafeStateDirective`）。

**明確排除的範圍（Out-of-Scope）**：CAP 1.0 不負責身分註冊（詳見 `FayID`）、不負責推理決策（詳見 `Ego`）、不承載社會貢獻計量（公譽鏈 `GMChain` 上的非貨幣美譽值 `MeriToken` 詳見 `Global-Merit-Chain`），且**嚴禁承載任何金融資金劃轉或支付清算指令**（所有 `domain_category == "fund_transfer"` 的請求一律拒絕）。

## 0.2 RFC 2119 與 RFC 8174 規範性用語對應聲明

本規範遵循 IETF RFC 2119 與 RFC 8174 的規範性關鍵字約定。當英文全大寫關鍵字 **MUST**、**MUST NOT**、**REQUIRED**、**SHALL**、**SHALL NOT**、**SHOULD**、**SHOULD NOT**、**RECOMMENDED**、**NOT RECOMMENDED**、**MAY**、**OPTIONAL** 出現，或下表所列正體中文規範性片語出現時，它們具有嚴格的規範性約束力；未按上述形式書寫的日常用詞不構成規範性要求：

| RFC 2119 / RFC 8174 英文關鍵字 | 正體中文規範性對應表述 | 規範性語意 |
|-------------------------------|----------------------|-----------|
| **MUST** / **SHALL** / **REQUIRED** | **必須** / **須** | 絕對強制要求；任一條不滿足即不得聲稱符合 CAP 1.0 |
| **MUST NOT** / **SHALL NOT** | **不得** / **嚴禁** | 絕對禁止行為；任何違反均構成協定不一致與安全違規 |
| **SHOULD** / **RECOMMENDED** | **應當** / **建議** | 強烈建議遵循；僅在充分評估安全影響並記錄理由時方可偏離 |
| **SHOULD NOT** / **NOT RECOMMENDED** | **不應** / **不建議** | 強烈建議避免；偏離前須完成顯式風險評估 |
| **MAY** / **OPTIONAL** | **可以** / **可選** | 真正可選行為；各實作不得假定對端必定提供或必定省略該能力 |

## 0.3 核心規範術語

本規範嚴格遵循體系術語基線，任何實作文件與程式碼註解 **MUST** 保持一致：

- **人類原型（Human Prime）**：`iFay` 所復刻並對其行為享有最終控制權與最高接管權的自然人主體（規範識別碼符合 `^hid_[a-z2-7]{16,}$`）。**嚴禁使用「宿主 / Host」指代人類原型。**
- **Fay（`iFay` / `coFay`）**：發起宿主資源控制請求的數位化身主體。
- **附身（Inhabit）**：將 `Fay` 執行時注入目標宿主使其具備受控操作能力的過程。
- **宿主（Host）**：被 `Fay` 附身並受 CAP 門控保護的**實體終端設備、感測致動器或軟體應用實例**（僅指設備或軟體，絕不指人）。
- **CAP 評估器（CAP Evaluator）**：部署在宿主可信邊界內、按預設拒絕管線執行 `CapEvaluationRequest → CapDecision` 判定的規範性執行元件。

## 0.4 三條正交版本軸與兩段式 `"1.0"` 版本紀律

CAP 採用三條互相正交的版本軸，實作 **MUST NOT** 將它們合併為單一字串或三段式 SemVer：

1. **協定版本（Protocol Version）**：唯一進入線格式的互操作契約識別，採用嚴格的兩段式 `MAJOR.MINOR`（不設 `PATCH` 段）。在線信封標頭記為 `"CAP/1.0"`，在 `CapEvaluationRequest.protocol_version` 與 `protocol.version` 欄位中固定編碼為兩段式字串 **`"1.0"`**（符合正規表示式 `^(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$`）。
   - **MAJOR 遞增**：僅用於破壞既有線格式或改變預設拒絕安全不變量的變更；跨 `MAJOR` 不保證相容。
   - **MINOR 遞增**：僅用於向後相容的可選欄位或列舉增補；同一 `MAJOR` 內高 `MINOR` 實作 **MUST** 相容至 `MAJOR.0`，並忽略未知可選欄位。
2. **文件狀態（Document Status）**：僅記錄於文件詮釋資料 `status` 欄位（取值為區分大小寫的 `Draft`、`Final`、`Deprecated`、`Obsolete` 四者之一），**SHALL NOT** 進入線格式或目錄路徑。
3. **編輯版次（Editorial Edition）**：以發布日期 `YYYY-MM-DD` 命名（CAP 1.0 首發定稿版次為 **`2025-10-25`**），僅承載不改變任何線格式與規範性語意的純文字修訂，**SHALL NOT** 進入線格式。

當 CAP 評估器收到 `protocol_version` 不屬於受支援協定版本（例如 CAP 1.0 評估器收到 `"2.0"` 或三段式 `"1.0.0"`）的請求時，**MUST** 立即拒絕並回傳 `decision = "DENY"`、`effective_criticality = "critical"`、`error_code = "E_PROTOCOL_VERSION_UNSUPPORTED"` 及數值診斷碼 `2098`，**SHALL NOT** 執行任何降級猜測。
