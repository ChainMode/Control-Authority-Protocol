# 第 3 章：驅動能力清單與不可逆地板

## 3.1 驅動能力清單（`DriverCapabilityManifest`）與密碼學驗簽

操作危重度的底線 **SHALL NOT** 由發起呼叫的 `Fay` 或外部未受控輸入決定，而 **MUST** 由宿主（`Host`）側經可信公開金鑰簽章的 `DriverCapabilityManifest` 權威宣告。清單包含以下核心欄位：

- `manifest_id`、`driver_id`、`version`、`issued_at`：驅動清單唯一識別碼、版本號與簽發時間戳記；
- `signer_key_id`：指向宿主本地信任錨對應表（`TrustAnchorMap`）中的公開金鑰條目識別碼；
- `resources`：非空的 `ResourceCapabilityDescriptor` 陣列，宣告每個 `resource_id`、可選的 `safe_states` 清單及非空的 `operations`（`OperationDescriptor`）清單；
- `signature_ed25519`：64 位元組（128 個十六進位字元）的 RFC 8032 Ed25519 數位簽章。

### 規範化驗簽流程

CAP 評估器 **MUST** 按以下步驟驗證清單真實性：

1. 檢查 `signature_ed25519` 是否為合法的 128 位十六進位字串，並在 `trust_anchors` 中查找 `signer_key_id`；若缺失、演算法不為 `"Ed25519"` 或公開金鑰不為 64 位十六進位（32 位元組原始公開金鑰），立即判定驗簽失敗。
2. 建構移除了 `signature_ed25519` 欄位後的無簽章清單物件，按 **RFC 8785 相容確定性規範化 JSON**（所有物件鍵按 UTF-8 字典序升冪排列、省略未定義可選欄位、無多餘空白字元）序列化為 UTF-8 位元組序列。
3. 使用信任錨的 Ed25519 公開金鑰對該 UTF-8 位元組序列執行標準 Ed25519 驗簽。

驗簽未通過時，評估器 **MUST** 立即回傳 `decision = "DENY"`、`effective_criticality = "critical"`、`error_code = "E_UNTRUSTED_MANIFEST"` 與 `diagnostic_code = 2005`。

## 3.2 未知資源與未知操作預設致命拒絕

在已通過 Ed25519 驗簽的 `DriverCapabilityManifest` 中：

- 若找不到與 `req.resource_id` 精確相符的資源描述符，或在相符資源下找不到與 `req.operation_id` 精確相符的操作描述符，CAP 評估器 **MUST** 將該次請求的 `effective_criticality` 強制設定為 `"critical"`，並立即回傳 `decision = "DENY"`、`error_code = "E_UNKNOWN_OPERATION"` 與 `diagnostic_code = 2004`。
- 實作 **SHALL NOT** 為未在清單中宣告的操作提供萬用字元放行或預設降級為 `routine`。

## 3.3 後果不可逆性軸（`ConsequenceIrreversibility`）地板規則

為防止驅動開發者誤將具有不可逆物理或資料破壞後果的操作標記為低危重度，每個 `OperationDescriptor` **MUST** 同時宣告 `criticality` 與 `consequence_irreversibility` 兩個欄位。評估器 **MUST** 先按以下不可逆地板函式計算清單底線危重度 `floor_criticality`：

| `consequence_irreversibility` 取值 | 典型宿主操作範例 | 強制危重度地板規則 (`floor_criticality`) |
|-----------------------------------|-----------------|-----------------------------------------|
| `reversible` | 讀取飛控姿態遙測、讀取環境溫度 | 保持 `operation.criticality` 不變 |
| `bounded_compensation` | 寫入附自動回退的受界 PID 參數 | 保持 `operation.criticality` 不變 |
| `irreversible_consequence` | 解鎖實體貨艙門閂、發送外部實體信標 | $\max(\texttt{operation.criticality}, \texttt{high})$ —— 底線至少抬升至 **`high`** |
| `irreversible_data_or_hardware` | 不可恢復儲存安全抹除、存在變磚風險的底層韌體刷寫 | **強制鎖定為 `critical`**（無論 `operation.criticality` 原值為何） |

例如，即便某驅動將 `unlock_cargo_latch` 的基礎 `criticality` 寫為 `sensitive`，只要其宣告了 `consequence_irreversibility = "irreversible_consequence"`，評估器計算出的 `floor_criticality` 即自動抬升為 `high`；同理，`flash_esc_firmware` 宣告 `irreversible_data_or_hardware` 時，`floor_criticality` 強制鎖定為 `critical`。

## 3.4 單調危重度上調與防降級夾緊（Escalation Clamping）

在取得 `floor_criticality` 後，CAP 允許上游委任憑據（`req.grant.criticality_override`）與當前呼叫方（`req.caller_criticality_override`）附加更嚴格的本地策略覆寫，但嚴格遵循**單調只升不降不變量**：

1. 令初始 `effective_criticality = floor_criticality`，初始 `escalation_clamped = false`。
2. 依序檢查 `req.grant.criticality_override` 與 `req.caller_criticality_override`（若存在）：
   - 若某覆寫值嚴格低於 `floor_criticality`（即 $\text{rank}(\text{override}) < \text{rank}(\text{floor\_criticality})$），評估器 **MUST** 忽略該降級企圖、保持不低於 `floor_criticality` 的等級，並將回應中的 **`escalation_clamped` 標記為 `true`** 以供安全稽核記錄；
   - 若某覆寫值大於或等於 `floor_criticality`，則更新 `effective_criticality = max(effective_criticality, override)`。

由此保證對任意請求恆成立：

$$\text{rank}(\texttt{effective\_criticality}) \ge \text{rank}(\texttt{floor\_criticality})$$
