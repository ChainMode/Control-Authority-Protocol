# 제4장: 고위험 인간 프라임 확인과 안전 상태

## 4.1 매개변수 결합형 명시적 `Human Prime` 확인 게이트(`HumanConfirmationProof`)

`effective_criticality`가 **`high`** 또는 **`critical`** 인 모든 작업(**최고 신뢰 등급 `G1` 세션 내부에서 실행되는 요청 포함**)에 대해, CAP 평가기는 요청에 포함된 `human_confirmation`(`HumanConfirmationProof`)을 강제로 검증해야 하며(**MUST**), 「자동화 편의성」이나 「과거 양호한 실행 이력」을 이유로 개별 확인을 면제해서는 안 된다(**SHALL NOT**).

1. **정규 식별자 검증**: `human_confirmation.human_prime_id`는 정규화된 `Human Prime`(인간 프라임) 식별자 정규식 `^hid_[a-z2-7]{16,}$`와 일치해야 한다(**MUST**).
2. **만료 신선도 검증**: `human_confirmation.expires_at_epoch_ms`는 현재 평가 타임스탬프 `req.now_epoch_ms`보다 엄격히 커야 한다(**MUST**).
3. **호스트 단말 고지 증명**: `human_confirmation.terminal_attested_disclosure`는 `true`여야 하며(**MUST**), `Fay`의 자체 보고 텍스트가 아닌 호스트의 신뢰된 인터페이스가 대상 리소스, 작업 및 비가역적 위험을 `Human Prime`에게 온전히 고지했음을 증명한다.
4. **매개변수 정규화 SHA-256 결합**: 현재 요청의 `req.params`를 사전순 키 정렬 정규화 JSON(§3.1 참조)으로 직렬화한 UTF-8 바이트열의 SHA-256 소문자 16진수 다이제스트(64자)를 계산했을 때, `human_confirmation.confirmed_params_sha256`가 이와 문자 단위로 완전히 일치해야 한다(**MUST**).

`human_confirmation`이 누락되었거나 위 네 가지 조건 중 하나라도 충족되지 않으면(예: 확인 후 `latch_id` 매개변수가 변조된 경우), 평가기는 즉시 `decision = "DENY"`, `error_code = "E_CONFIRMATION_REQUIRED"`, `diagnostic_code = 2006`을 반환해야 한다(**MUST**).

## 4.2 `G0` 긴급 인수와 비차단 안전 상태 지시

`Human Prime`(인간 프라임)은 언제나 호스트에 대한 절대적 최우선 제어권 인수 권한을 가진다. 요청에서 `g0_override == true` 또는 `grant.mandate_binding.session_grade == "G0"`이 감지된 경우:

1. **즉시 선점 거부**: CAP 평가기는 Mandate 만료·모드 검사를 수행하기 전에 즉시 `Fay`의 제어 요청을 차단하고 `decision = "DENY"`, `error_code = "E_G0_EMERGENCY_OVERRIDE"`, `diagnostic_code = 2003`을 반환해야 한다(**MUST**).
2. **결정론적 안전 상태 지시(`G0SafeStateDirective`)**:
   - 대상 `ResourceCapabilityDescriptor.safe_states`가 비어 있지 않으면 평가기는 첫 번째 우선 안전 상태 `safe_states[0].safe_state_id`를 선택하여 다음을 출력해야 한다(**MUST**):
     `{ "action": "enter_safe_state", "safe_state_id": "<safe_states[0].safe_state_id>", "blocks_human_takeover": false }`
   - 대상 리소스에 `safe_states`가 선언되지 않았거나 빈 목록이면 평가기는 다음을 출력해야 한다(**MUST**):
     `{ "action": "terminate_and_alert", "blocks_human_takeover": false }`(진행 중인 에이전트 동작을 즉시 중단하고 `Human Prime`에게 명시적 경보를 발생시킴)
3. **비차단 불변식**: 어떠한 상황에서도 `safe_state_directive.blocks_human_takeover`는 항상 불리언 상수 `false`여야 한다(**MUST**). 호스트의 안전 상태 전환이나 정리 절차가 `Human Prime`의 물리적·대화형 직접 제어권 회수를 차단, 잠금 또는 지연시켜서는 안 된다(**SHALL NOT**).

## 4.3 표준 에러 코드 및 수치 진단 코드표

CAP 1.0 와이어 형식은 안정적인 대문자 스네이크 케이스 문자열(`CapErrorCode`)을 규범 에러 코드로 사용하며, 테스트 벡터 및 진단 로그를 위해 1대1 대응하는 수치 진단 코드(`2001`–`2099`)를 결합한다.

| 규범 에러 코드 (`error_code`) | 수치 진단 코드 (`diagnostic_code`) | 발생 단계 및 규범적 의미 |
|-------------------------------|------------------------------------|--------------------------|
| `E_WEAK_MANDATE_BINDING` | `2001` | `high`/`critical`에서 `model_a_plus_b`(또는 파생 증명·온라인 신선도)가 결여되었거나, `sensitive`에서 오프라인 캐시 `model_c_offline_cache`를 사용한 경우 |
| `E_GRADE_INSUFFICIENT` | `2002` | 세션 등급이 `grant.min_grade` 미만이거나 `FayingGrade × AccessMode × Criticality` 매트릭스를 충족하지 못한 경우 |
| `E_G0_EMERGENCY_OVERRIDE` | `2003` | `Human Prime`의 `G0` 긴급 인수가 발동하여 `Fay` 제어를 거부하고 비차단 `safe_state_directive`를 방출한 경우 |
| `E_UNKNOWN_OPERATION` | `2004` | 요청된 `resource_id` 또는 `operation_id`가 서명 검증된 `DriverCapabilityManifest`에 선언되지 않은 경우 |
| `E_UNTRUSTED_MANIFEST` | `2005` | `DriverCapabilityManifest`의 서명 누락, 신뢰 앵커 부재 또는 Ed25519 서명 검증 실패 |
| `E_CONFIRMATION_REQUIRED` | `2006` | `high`/`critical` 작업에서 미만료·단말 고지 증명·매개변수 SHA-256 일치를 만족하는 `HumanConfirmationProof`가 없거나 불일치하는 경우 |
| `E_OUT_OF_SCOPE_FUND_TRANSFER` | `2007` | 요청 또는 작업이 `domain_category == "fund_transfer"`를 선언하여 CAP 1.0 범위를 벗어난 경우 |
| `E_MANDATE_INVALID` | `2008` | Mandate가 철회·만료되었거나 온라인 모델에서 `online_fresh == false`이거나 주체·리소스·모드가 불일치하는 경우 |
| `E_PROTOCOL_VERSION_UNSUPPORTED` | `2098` | `protocol_version`이 지원되는 2세그먼트 문자열 `"1.0"`과 일치하지 않는 경우 |
| `E_PROTOCOL` | `2099` | 프로토콜 메시지 구조 오류 또는 폴백 에러. 레거시 별칭 `E_INVALID_MESSAGE`는 입력 정규화 시 반드시 `E_PROTOCOL`로 매핑해야 한다(**MUST**) |

## 4.4 구현 적합성(Conformance) 판정 기준

단말, 드라이버 호스트 또는 런타임 구현이 **CAP 1.0(`2025-10-25` 판차)** 적합성을 선언하려면 다음의 검증 가능한 조건을 모두 충족해야 한다(**MUST**).

1. 제0장~제4장에 정의된 기본 거부 8단계 평가 파이프라인, 단조 위험도 하한, 3차원 등급 매트릭스, 매개변수 SHA-256 결합형 `Human Prime` 확인 게이트 및 `G0` 비차단 안전 상태 지시를 완전히 구현할 것
2. 입출력 구조가 `schemas/cap-1.0.cddl` 및 `schemas/cap-1.0.json`과 엄격히 일치할 것
3. 공식 규범 의미론 테스트 벡터 모음 `vectors/semantic/d1-d7-conformance.json`의 전체 14개 벡터(`V01`–`V14`)를 실행하여 판정 결과, 유효 위험도, 강등 클램핑 플래그, 에러 코드, 진단 코드 및 안전 상태 지시가 기대값과 **100% 일치**할 것
