# 제0장: 개요와 규범적 용어

## 0.1 프로토콜 목적과 범위

**제어 권한 프로토콜(Control Authority Protocol, CAP)** 은 디지털 아바타(`iFay` 개인 아바타와 `coFay` 공공 역할 아바타를 통칭하는 `Fay`)와 빙의(`Inhabit`) 대상 호스트(`Host`, 즉 제어 대상 하드웨어 단말 장치 또는 클라이언트 애플리케이션) 사이에 위치하는 기본 거부(Default-Deny) 제어권 게이트 프로토콜이다. CAP은 상위 위임 인가를 개별 호스트 리소스 및 드라이버 작업에 대한 결정론적 허용·거부 판정으로 변환하여, 비가역적인 물리 동작이나 중대한 시스템 변경이 실행되기 전에 암호학적 능력 하한과 `Human Prime`(인간 프라임)의 의사를 엄격히 강제한다.

CAP 1.0의 규범적 범위는 다음 항목을 포괄한다.

1. 제어권 평가 요청(`CapEvaluationRequest`)과 결정론적 판정 출력(`CapDecision`)의 데이터 모델 및 와이어 형식
2. 암호화 서명된 드라이버 능력 매니페스트(`DriverCapabilityManifest`) 검증, 기본 위험도 하한 및 결과 비가역성 하한 산출
3. 상위 `Faying-Protocol` 위임 증빙(`MandateEvidence`)에 대한 온라인 신선도 및 세션 파생 바인딩 검증
4. `FayingGrade × AccessMode × Criticality` 3차원 등급별 접근 제어 매트릭스
5. 고위험·치명적 작업에 대한 매개변수 SHA-256 결합형 명시적 `Human Prime` 확인 게이트(`HumanConfirmationProof`)
6. `Human Prime`의 `G0` 긴급 인수 선점 및 비차단 안전 상태 지시(`G0SafeStateDirective`)

**명시적 범위 제외(Out-of-Scope)**: CAP 1.0은 신원 등록(`FayID` 참조), 인지 추론(`Ego` 참조), 사회 공헌 계량(`GMChain` 상의 비화폐성 `MeriToken`은 `Global-Merit-Chain` 참조)을 다루지 않는다. 또한 **금융 자금 이체 및 결제 정산(`fund_transfer`)은 프로토콜 범위에서 엄격히 제외**되며, `domain_category == "fund_transfer"`인 모든 요청은 조건 없이 거부된다.

## 0.2 RFC 2119 및 RFC 8174 규범적 용어 매핑 선언

본 사양서는 IETF RFC 2119 및 RFC 8174 규범 키워드 규칙을 따른다. 영문 대문자 키워드 **MUST**, **MUST NOT**, **REQUIRED**, **SHALL**, **SHALL NOT**, **SHOULD**, **SHOULD NOT**, **RECOMMENDED**, **NOT RECOMMENDED**, **MAY**, **OPTIONAL** 또는 아래 표에 정의된 한국어 규범 표현이 사용될 때 엄격한 규범적 효력을 가진다. 그 외 일상적 서술은 규범적 요구사항을 구성하지 않는다.

| RFC 2119 / RFC 8174 영문 키워드 | 한국어 규범 대응 표현 | 규범적 의미 |
|---------------------------------|-----------------------|-------------|
| **MUST** / **SHALL** / **REQUIRED** | **반드시 ~해야 한다** / **필수이다** | 절대적 강제 요구사항. 하나라도 충족하지 못하면 CAP 1.0 적합성을 주장할 수 없다 |
| **MUST NOT** / **SHALL NOT** | **절대 ~해서는 안 된다** / **금지된다** | 절대적 금지 사항. 위반 시 프로토콜 부적합 및 보안 위반에 해당한다 |
| **SHOULD** / **RECOMMENDED** | **~해야 한다(권장)** / **권장된다** | 강력 권장 사항. 보안 영향을 충분히 검토하고 사유를 기록한 경우에만 예외가 허용된다 |
| **SHOULD NOT** / **NOT RECOMMENDED** | **~하지 않아야 한다(비권장)** / **권장되지 않는다** | 회피 권장 사항. 편차 적용 전 명시적 위험 평가가 필요하다 |
| **MAY** / **OPTIONAL** | **~할 수 있다** / **선택 사항이다** | 순수 선택 기능. 상대 구현이 해당 기능의 존재나 생략을 전제해서는 안 된다 |

## 0.3 핵심 규범 용어

모든 구현 문서와 코드 주석은 다음 용어 기준을 **MUST** 일관되게 준수해야 한다.

- **`Human Prime`(인간 프라임)**: `iFay`가 복제한 대상이자 최종 책임 및 최우선 제어권 인수 권한을 보유한 자연인 주체(정규 식별자는 `^hid_[a-z2-7]{16,}$` 패턴을 따름). **자연인을 지칭하기 위해 「호스트 / Host」라는 용어를 절대 사용해서는 안 된다(MUST NOT).**
- **`Fay`(`iFay` / `coFay`)**: 호스트 리소스 제어 요청을 발신하는 디지털 아바타 주체.
- **빙의(`Inhabit`)**: 대상 호스트에 `Fay` 런타임을 주입하여 통제 가능한 상태로 만드는 과정.
- **호스트(`Host`)**: `Fay`가 빙의하여 CAP 게이트의 보호를 받는 **물리 단말 장치, 센서·액추에이터 또는 클라이언트 소프트웨어 애플리케이션**(오직 기기나 앱만을 뜻하며, 결코 사람을 뜻하지 않음).
- **CAP 평가기(CAP Evaluator)**: 호스트 신뢰 경계 내부에 배치되어 기본 거부 파이프라인에 따라 `CapEvaluationRequest → CapDecision` 판정을 수행하는 규범 컴포넌트.

## 0.4 직교하는 3개 버전 축과 2세그먼트 `"1.0"` 버전 규율

CAP은 서로 직교하는 세 가지 버전 축을 사용하며, 구현은 이를 단일 번호나 3세그먼트 SemVer로 합쳐서는 안 된다(**MUST NOT**).

1. **프로토콜 버전(Protocol Version)**: 와이어 형식에 진입하는 유일한 상호운용 계약 식별자로, `PATCH`가 없는 엄격한 2세그먼트 `MAJOR.MINOR` 형식을 따른다. 와이어 봉투 헤더에서는 `"CAP/1.0"`으로 표기하며, `CapEvaluationRequest.protocol_version` 및 `protocol.version` 필드에서는 2세그먼트 문자열 **`"1.0"`**(정규식 `^(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$`)으로 고정된다.
   - **MAJOR 증가**: 기존 와이어 형식이나 기본 거부 보안 불변식을 깨뜨리는 파괴적 변경에만 적용된다. 서로 다른 `MAJOR` 간 상호운용은 보장되지 않는다.
   - **MINOR 증가**: 하위 호환되는 선택 필드 또는 열거값 추가에만 적용된다. 동일 `MAJOR` 내 상위 `MINOR` 구현은 반드시 `MAJOR.0`까지 하위 호환성을 유지하고(**MUST**), 알 수 없는 선택 필드를 무시해야 한다.
2. **문서 상태(Document Status)**: 프런트매터 `status` 필드(대소문자를 구분하는 `Draft`, `Final`, `Deprecated`, `Obsolete` 중 하나)에만 기록되며, 와이어 형식이나 디렉터리 경로에 포함되어서는 안 된다(**SHALL NOT**).
3. **편집 판차(Editorial Edition)**: 배포 날짜 `YYYY-MM-DD`(CAP 1.0 최초 확정 판차는 **`2025-10-25`**)로 식별되며, 와이어 형식이나 규범적 의미를 바꾸지 않는 순수 문구 교정만을 담는다. 와이어 형식에 진입해서는 안 된다(**SHALL NOT**).

CAP 평가기가 지원하지 않는 `protocol_version`(예: `"2.0"` 또는 3세그먼트 `"1.0.0"`)을 수신한 경우, 임의 다운그레이드 없이 즉시 거부하고(**MUST**) `decision = "DENY"`, `effective_criticality = "critical"`, `error_code = "E_PROTOCOL_VERSION_UNSUPPORTED"`, 진단 코드 `2098`을 반환해야 한다.
