# 제3장: 드라이버 능력 매니페스트와 비가역성 하한

## 3.1 드라이버 능력 매니페스트(`DriverCapabilityManifest`)와 암호화 서명 검증

작업 위험도의 기준 하한은 호출 측 `Fay`나 외부 비신뢰 입력에 의해 결정되어서는 안 되며(**SHALL NOT**), 호스트(`Host`) 측에서 신뢰된 공개키로 서명된 `DriverCapabilityManifest`에 의해 권위 있게 선언되어야 한다(**MUST**). 매니페스트는 다음 핵심 필드를 포함한다.

- `manifest_id`, `driver_id`, `version`, `issued_at`: 드라이버 매니페스트 고유 식별자, 버전 및 발급 시각
- `signer_key_id`: 호스트 로컬 신뢰 앵커 맵(`TrustAnchorMap`) 내 공개키 항목 식별자
- `resources`: 비어 있지 않은 `ResourceCapabilityDescriptor` 배열로, 각 `resource_id`, 선택적 `safe_states` 목록 및 비어 있지 않은 `operations`(`OperationDescriptor`) 목록을 선언함
- `signature_ed25519`: 64바이트(128자리 16진수 문자열) RFC 8032 Ed25519 디지털 서명

### 정규화 서명 검증 절차

CAP 평가기는 다음 절차에 따라 매니페스트의 진정성을 검증해야 한다(**MUST**).

1. `signature_ed25519`가 유효한 128자리 16진수 문자열인지 확인하고 `trust_anchors`에서 `signer_key_id`를 조회한다. 항목이 없거나 `algorithm`이 `"Ed25519"`가 아니거나 `public_key_raw_hex`가 64자리 16진수(32바이트 원시 공개키)가 아니면 즉시 검증 실패로 처리한다.
2. 매니페스트 객체에서 `signature_ed25519` 필드를 제거한 비서명 페이로드를 구성하고, **RFC 8785 호환 결정론적 정규화 JSON**(모든 객체 키를 사전순 오름차순 정렬, 미정의 선택 필드 생략, 불필요한 공백 제거)으로 직렬화하여 UTF-8 바이트열을 얻는다.
3. 신뢰 앵커의 Ed25519 공개키로 해당 UTF-8 바이트열에 대한 표준 Ed25519 서명 검증을 수행한다.

서명 검증에 실패하면 평가기는 즉시 `decision = "DENY"`, `effective_criticality = "critical"`, `error_code = "E_UNTRUSTED_MANIFEST"`, `diagnostic_code = 2005`를 반환해야 한다(**MUST**).

## 3.2 미선언 리소스 및 미선언 작업의 기본 치명적 거부

Ed25519 서명 검증을 통과한 `DriverCapabilityManifest` 내에서:

- `req.resource_id`와 정확히 일치하는 리소스 기술자가 없거나, 일치한 리소스 아래에 `req.operation_id`와 정확히 일치하는 작업 기술자가 없으면, CAP 평가기는 해당 요청의 `effective_criticality`를 강제로 `"critical"`로 설정하고 즉시 `decision = "DENY"`, `error_code = "E_UNKNOWN_OPERATION"`, `diagnostic_code = 2004`를 반환해야 한다(**MUST**).
- 구현은 매니페스트에 선언되지 않은 작업에 대해 와일드카드 허용이나 `routine` 기본 강등을 제공해서는 안 된다(**SHALL NOT**).

## 3.3 결과 비가역성 축(`ConsequenceIrreversibility`) 하한 규칙

드라이버 작성자가 비가역적 물리 결과나 데이터 파기를 수반하는 작업에 낮은 위험도를 잘못 지정하는 오류를 막기 위해, 모든 `OperationDescriptor`는 `criticality`와 `consequence_irreversibility` 두 필드를 모두 필수로 선언해야 한다(**MUST**). 평가기는 다음 비가역성 하한 함수로 기준 하한 `floor_criticality`를 먼저 산출해야 한다(**MUST**).

| `consequence_irreversibility` 값 | 대표 호스트 작업 예시 | 강제 위험도 하한 규칙 (`floor_criticality`) |
|----------------------------------|-----------------------|---------------------------------------------|
| `reversible` | 비행 제어기 텔레메트리 조회, 주변 온도 읽기 | `operation.criticality` 유지 |
| `bounded_compensation` | 자동 복구 범위 내 유계 PID 계수 갱신 | `operation.criticality` 유지 |
| `irreversible_consequence` | 화물칸 물리 걸쇠 해제, 외부 물리 비콘 송출 | $\max(\texttt{operation.criticality}, \texttt{high})$ — 하한을 최소 **`high`** 로 상향 |
| `irreversible_data_or_hardware` | 복구 불가 보안 삭제, 브릭 위험이 있는 저수준 펌웨어 플래싱 | **`critical`로 강제 고정**(원래 `operation.criticality` 값과 무관) |

예를 들어 매니페스트에서 `unlock_cargo_latch`의 기본 `criticality`가 `sensitive`로 기재되어 있더라도 `consequence_irreversibility = "irreversible_consequence"`이면 `floor_criticality`는 자동으로 `high`로 격상된다. 마찬가지로 `flash_esc_firmware`가 `irreversible_data_or_hardware`를 가지면 `floor_criticality`는 강제로 `critical`이 된다.

---

## 3.4 단조 위험도 상향 및 강등 클램핑(Escalation Clamping)

`floor_criticality`를 산출한 뒤 CAP은 상위 인가 증빙(`req.grant.criticality_override`)과 호출 측 요청(`req.caller_criticality_override`)이 더 엄격한 로컬 정책 오버라이드를 부과하는 것을 허용하되, **단조 상향 전용·하향 금지 불변식**을 엄격히 강제한다.

1. 초기값을 `effective_criticality = floor_criticality`, `escalation_clamped = false`로 둔다.
2. `req.grant.criticality_override`와 `req.caller_criticality_override`(존재하는 경우)를 순서대로 검사한다.
   - 오버라이드 값이 `floor_criticality`보다 엄격히 낮으면($\text{rank}(\text{override}) < \text{rank}(\text{floor\_criticality})$), 평가기는 해당 강등 시도를 무시하고 `floor_criticality` 이상의 등급을 유지하며 감사 추적을 위해 응답의 **`escalation_clamped`를 `true`로 설정**해야 한다(**MUST**).
   - 오버라이드 값이 `floor_criticality` 이상이면 `effective_criticality = max(effective_criticality, override)`로 갱신한다.

이에 따라 모든 요청에 대해 다음 불변식이 항상 성립한다.

$$\text{rank}(\texttt{effective\_criticality}) \ge \text{rank}(\texttt{floor\_criticality})$$
