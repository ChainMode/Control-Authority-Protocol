# Глава 3: Манифест возможностей драйвера и порог необратимости

## 3.1 Проверка подписанного `DriverCapabilityManifest`

Базовая критичность операции **НЕ ДОЛЖНА** (**SHALL NOT**) определяться вызывающим аватаром `Fay` или непроверенными внешними метаданными; она **ДОЛЖНА** (**MUST**) поступать из размещённого на стороне Host документа `DriverCapabilityManifest`, криптографически подписанного доверенным центром. Каждый манифест включает:

- `manifest_id`, `driver_id`, `version`, `issued_at`: Уникальный идентификатор манифеста, идентификатор драйвера, строку версии и время выпуска;
- `signer_key_id`: Идентификатор ключа, ссылающийся на запись в локальной таблице `TrustAnchorMap` на Host;
- `resources`: Непустой массив дескрипторов `ResourceCapabilityDescriptor`, содержащих `resource_id`, необязательный список `safe_states` и непустой список `operations` (`OperationDescriptor`);
- `signature_ed25519`: 64-байтную (128 шестнадцатеричных символов) подпись Ed25519 по стандарту RFC 8032.

### Каноническая процедура проверки подписи

Вычислитель CAP **ДОЛЖЕН** (**MUST**) проверять подлинность манифеста в следующем порядке:

1. Убедиться, что `signature_ed25519` представляет собой корректную 128-символьную шестнадцатеричную строку, и найти `signer_key_id` в `trust_anchors`. Если якорь доверия отсутствует, `algorithm != "Ed25519"` либо `public_key_raw_hex` не образует корректную 64-символьную шестнадцатеричную строку (32-байтный открытый ключ Ed25519), проверка немедленно завершается отказом.
2. Сформировать неподписанный объект манифеста без поля `signature_ed25519` и сериализовать его в байты UTF-8 в виде **детерминированного канонического JSON, совместимого с RFC 8785** (лексикографическая сортировка ключей объектов, пропуск неопределённых необязательных полей, отсутствие лишних пробелов).
3. Проверить 64-байтную подпись Ed25519 над полученными байтами UTF-8 по открытому ключу якоря доверия.

При неуспешной проверке вычислитель **ДОЛЖЕН** (**MUST**) немедленно вернуть `decision = "DENY"`, `effective_criticality = "critical"`, `error_code = "E_UNTRUSTED_MANIFEST"` и `diagnostic_code = 2005`.

## 3.2 Отказ с уровнем `critical` по умолчанию для неизвестных ресурсов и операций

В пределах проверенного по подписи `DriverCapabilityManifest`:

- Если ни один `ResourceCapabilityDescriptor` не совпадает с `req.resource_id` либо внутри найденного ресурса ни один `OperationDescriptor` не совпадает с `req.operation_id`, вычислитель CAP **ДОЛЖЕН** (**MUST**) присвоить `effective_criticality` значение `"critical"` и немедленно вернуть `decision = "DENY"`, `error_code = "E_UNKNOWN_OPERATION"` и `diagnostic_code = 2004`.
- Реализации **НЕ ДОЛЖНЫ** (**SHALL NOT**) поддерживать допуск по маске или считать необъявленные операции принадлежащими уровню `routine`.

## 3.3 Порог необратимости последствий (`ConsequenceIrreversibility`)

Чтобы ошибочно настроенный драйвер не занизил уровень физически или программно разрушительных действий, каждый `OperationDescriptor` **ДОЛЖЕН** (**MUST**) объявлять и `criticality`, и `consequence_irreversibility`. Вычислитель **ДОЛЖЕН** (**MUST**) сначала рассчитать нижний порог `floor_criticality`:

| Значение `consequence_irreversibility` | Типовая операция на Host | Обязательное правило порога (`floor_criticality`) |
|----------------------------------------|--------------------------|---------------------------------------------------|
| `reversible` | Чтение телеметрии полётного контроллера или датчиков температуры | Сохраняет `operation.criticality` |
| `bounded_compensation` | Подстройка коэффициентов PID с ограниченным автоматическим откатом | Сохраняет `operation.criticality` |
| `irreversible_consequence` | Открытие физического грузового замка или передача внешнего радиомаяка | $\max(\texttt{operation.criticality}, \texttt{high})$ — порог не ниже **`high`** |
| `irreversible_data_or_hardware` | Безвозвратное безопасное стирание хранилища или прошивка ESC с риском повреждения оборудования | **Жёстко фиксируется на `critical`** независимо от заявленного `operation.criticality` |

Например, даже если операция `unlock_cargo_latch` указывает базовый уровень `criticality = "sensitive"`, признак `consequence_irreversibility = "irreversible_consequence"` автоматически поднимает `floor_criticality` до `high`; аналогично `flash_esc_firmware` с признаком `irreversible_data_or_hardware` жёстко фиксируется на `critical`.

## 3.4 Монотонное повышение критичности и отсечение понижений

Поверх порога `floor_criticality` CAP разрешает вышестоящему разрешению (`req.grant.criticality_override`) и вызывающему узлу (`req.caller_criticality_override`) монотонно ужесточать политику, полностью блокируя попытки понижения:

1. Установить `effective_criticality = floor_criticality` и `escalation_clamped = false`.
2. Проверить `req.grant.criticality_override` и `req.caller_criticality_override` (если заданы):
   - Если переопределение строго ниже `floor_criticality` ($\text{rank}(\text{override}) < \text{rank}(\text{floor\_criticality})$), вычислитель **ДОЛЖЕН** (**MUST**) проигнорировать попытку понижения, сохранить уровень не ниже `floor_criticality` и выставить **`escalation_clamped = true`** в `CapDecision` для аудиторской прослеживаемости;
   - Иначе обновить `effective_criticality = max(effective_criticality, override)`.

Тем самым любое вычисление CAP соблюдает инвариант:

$$\text{rank}(\texttt{effective\_criticality}) \ge \text{rank}(\texttt{floor\_criticality})$$
