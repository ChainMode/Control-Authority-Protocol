# 第 3 章：ドライバ能力マニフェストと不可逆性フロア

## 3.1 ドライバ能力マニフェスト（`DriverCapabilityManifest`）と暗号署名検証

操作重大度のベースライン下限は、呼び出し元の `Fay` や外部の非信頼入力によって決定されてはならず（**SHALL NOT**）、ホスト（`Host`）側で信頼された公開鍵により署名された `DriverCapabilityManifest` によって権威的に宣言されなければならない（**MUST**）。マニフェストは以下の主要フィールドを持つ。

- `manifest_id`、`driver_id`、`version`、`issued_at`：ドライバマニフェストの一意識別子、バージョン、および発行日時
- `signer_key_id`：ホストのローカル信頼アンカーマップ（`TrustAnchorMap`）内の公開鍵エントリ識別子
- `resources`：1 件以上の `ResourceCapabilityDescriptor` 配列。各要素は `resource_id`、任意の `safe_states` リスト、および 1 件以上の `operations`（`OperationDescriptor`）リストを宣言する
- `signature_ed25519`：64 バイト（128 桁の 16 進文字列）の RFC 8032 Ed25519 デジタル署名

### 正規化署名検証手順

CAP 評価器は以下の手順でマニフェストの真正性を検証しなければならない（**MUST**）。

1. `signature_ed25519` が有効な 128 文字の 16 進文字列であることを確認し、`trust_anchors` から `signer_key_id` を検索する。エントリが存在しない、`algorithm` が `"Ed25519"` でない、または `public_key_raw_hex` が 64 文字の 16 進文字列（32 バイト生公開鍵）でない場合は直ちに検証失敗とする。
2. マニフェストオブジェクトから `signature_ed25519` フィールドを除いた未署名ペイロードを構築し、**RFC 8785 互換の決定論的正規化 JSON**（すべてのオブジェクトキーを辞書順昇順にソート、未定義の任意フィールドを省略、余分な空白なし）として UTF-8 バイト列にシリアライズする。
3. 信頼アンカーの Ed25519 公開鍵を用いて当該 UTF-8 バイト列に対する標準 Ed25519 署名検証を実行する。

署名検証に失敗した場合、評価器は直ちに `decision = "DENY"`、`effective_criticality = "critical"`、`error_code = "E_UNTRUSTED_MANIFEST"`、`diagnostic_code = 2005` を返さなければならない（**MUST**）。

## 3.2 未知のリソースおよび未知の操作に対するデフォルト致命的拒否

Ed25519 署名検証を通過した `DriverCapabilityManifest` において：

- `req.resource_id` に完全一致するリソース記述子が存在しない場合、または該当リソース配下に `req.operation_id` に完全一致する操作記述子が存在しない場合、CAP 評価器は当該リクエストの `effective_criticality` を強制的に `"critical"` に設定し、直ちに `decision = "DENY"`、`error_code = "E_UNKNOWN_OPERATION"`、`diagnostic_code = 2004` を返さなければならない（**MUST**）。
- 実装はマニフェスト未宣言の操作に対してワイルドカード許可を与えたり、`routine` へデフォルト引き下げを行ったりしてはならない（**SHALL NOT**）。

## 3.3 結果不可逆性軸（`ConsequenceIrreversibility`）のフロア規則

ドライバ作成者が不可逆的な物理的影響やデータ破壊を伴う操作に誤って低い重大度を設定することを防ぐため、各 `OperationDescriptor` は `criticality` と `consequence_irreversibility` の双方を必須フィールドとして宣言しなければならない（**MUST**）。評価器は以下の不可逆性フロア関数を適用してベースライン下限 `floor_criticality` を算出しなければならない（**MUST**）。

| `consequence_irreversibility` の値 | 代表的なホスト操作例 | 強制重大度フロア規則 (`floor_criticality`) |
|------------------------------------|----------------------|-------------------------------------------|
| `reversible` | フライトコントローラのテレメトリ読み取り、温度取得 | `operation.criticality` をそのまま維持 |
| `bounded_compensation` | 自動ロールバック付きの有界 PID 係数更新 | `operation.criticality` をそのまま維持 |
| `irreversible_consequence` | 物理貨物ラッチの解錠、外部物理ビーコン送信 | $\max(\texttt{operation.criticality}, \texttt{high})$ — 下限を少なくとも **`high`** に引き上げる |
| `irreversible_data_or_hardware` | 回復不能なセキュアストレージ消去、文鎮化リスクを伴う低レイヤファームウェア書き換え | **強制的に `critical` に固定**（元の `operation.criticality` に依らない） |

たとえば、マニフェスト上で `unlock_cargo_latch` の基礎 `criticality` が `sensitive` と記述されていても、`consequence_irreversibility = "irreversible_consequence"` である限り `floor_criticality` は自動的に `high` へ引き上げられる。同様に、`flash_esc_firmware` が `irreversible_data_or_hardware` を持つ場合、`floor_criticality` は強制的に `critical` となる。

---

## 3.4 単調重大度引き上げとダウングレード抑制（Escalation Clamping）

`floor_criticality` の算出後、CAP は上位の認可証憑（`req.grant.criticality_override`）および呼び出し元リクエスト（`req.caller_criticality_override`）による追加的な厳格化オーバーライドを許容するが、**単調引き上げのみ・引き下げ禁止の不変条件**を厳格に強制する。

1. 初期値を `effective_criticality = floor_criticality`、`escalation_clamped = false` とする。
2. `req.grant.criticality_override` および `req.caller_criticality_override`（指定されている場合）を順に検査する。
   - オーバーライド値が `floor_criticality` より厳密に低い場合（$\text{rank}(\text{override}) < \text{rank}(\text{floor\_criticality})$）、評価器はその引き下げ試行を無視し、`floor_criticality` 以上の重大度を維持した上で、監査証跡のためレスポンスの **`escalation_clamped` を `true` に設定**しなければならない（**MUST**）。
   - オーバーライド値が `floor_criticality` 以上である場合、`effective_criticality = max(effective_criticality, override)` へ更新する。

これにより、あらゆる評価において次の不変条件が常に成立する。

$$\text{rank}(\texttt{effective\_criticality}) \ge \text{rank}(\texttt{floor\_criticality})$$
