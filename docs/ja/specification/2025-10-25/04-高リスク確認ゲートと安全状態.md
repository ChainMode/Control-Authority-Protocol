# 第 4 章：高リスク確認ゲートと安全状態

## 4.1 パラメータ束縛型の明示的 `Human Prime` 確認ゲート（`HumanConfirmationProof`）

`effective_criticality` が **`high`** または **`critical`** となるすべての操作（**最高信頼グレード `G1` セッション内の要求を含む**）について、CAP 評価器はリクエストに添付された `human_confirmation`（`HumanConfirmationProof`）を強制的に検証しなければならず（**MUST**）、「自動化の利便性」や「過去の良好な実行履歴」を理由に個別確認を免除してはならない（**SHALL NOT**）。

1. **正規識別子検証**：`human_confirmation.human_prime_id` は正規化された `Human Prime`（人間プライム）識別子の正規表現 `^hid_[a-z2-7]{16,}$` に一致しなければならない（**MUST**）。
2. **有効期限の鮮度検証**：`human_confirmation.expires_at_epoch_ms` は評価時刻 `req.now_epoch_ms` より厳密に大きくなければならない（**MUST**）。
3. **ホスト端末による開示証明**：`human_confirmation.terminal_attested_disclosure` は `true` でなければならず（**MUST**）、`Fay` の自己申告テキストではなくホストの信頼された UI を通じて対象リソース・操作・不可逆リスクが `Human Prime` に完全に提示されたことを証明する。
4. **パラメータ正規化 SHA-256 束縛**：当該リクエストの `req.params` をキー辞書順ソート正規化 JSON（§3.1 参照）へシリアライズした UTF-8 バイト列の SHA-256 小文字 16 進ダイジェスト（64 文字）を算出し、`human_confirmation.confirmed_params_sha256` がそれと完全に一致しなければならない（**MUST**）。

`human_confirmation` が欠落している場合、または上記 4 条件のいずれか 1 つでも満たされない場合（例：確認後にパラメータ `latch_id` が改ざんされた場合）、評価器は直ちに `decision = "DENY"`、`error_code = "E_CONFIRMATION_REQUIRED"`、`diagnostic_code = 2006` を返さなければならない（**MUST**）。

## 4.2 `G0` 緊急引き継ぎと非ブロッキング安全状態指示

`Human Prime`（人間プライム）はいかなる時点においてもホストに対する絶対的な最優先引き継ぎ権を持つ。リクエストで `g0_override == true` または `grant.mandate_binding.session_grade == "G0"` が検出された場合：

1. **即時プリエンプション拒否**：CAP 評価器は Mandate の期限やモード検証を行う前に直ちに `Fay` の制御リクエストを遮断し、`decision = "DENY"`、`error_code = "E_G0_EMERGENCY_OVERRIDE"`、`diagnostic_code = 2003` を返さなければならない（**MUST**）。
2. **決定論的安全状態指示（`G0SafeStateDirective`）**：
   - 対象 `ResourceCapabilityDescriptor.safe_states` が空でない場合、評価器は先頭の優先安全状態 `safe_states[0].safe_state_id` を選択し、次を出力しなければならない（**MUST**）：
     `{ "action": "enter_safe_state", "safe_state_id": "<safe_states[0].safe_state_id>", "blocks_human_takeover": false }`
   - 対象リソースに `safe_states` が宣言されていない（または空配列である）場合、評価器は次を出力しなければならない（**MUST**）：
     `{ "action": "terminate_and_alert", "blocks_human_takeover": false }`（実行中のエージェント操作を直ちに中止し、`Human Prime` へ明示的な警報を発する）
3. **非ブロッキング不変条件**：いかなる状況においても `safe_state_directive.blocks_human_takeover` は常にブール定数 `false` でなければならない（**MUST**）。ホスト側の安全状態遷移やクリーンアップ処理が、`Human Prime` による物理的・対話的な直接引き継ぎをブロック、ロック、または遅延させてはならない（**SHALL NOT**）。

## 4.3 標準エラーコードおよび数値診断コード一覧

CAP 1.0 のワイヤ形式は安定した大文字スネークケース文字列（`CapErrorCode`）を規範エラーコードとして使用し、テストベクタおよび診断ログ向けに 1 対 1 対応する数値診断コード（`2001`–`2099`）を付与する。

| 規範エラーコード (`error_code`) | 数値診断コード (`diagnostic_code`) | 発生条件および規範的意味 |
|---------------------------------|------------------------------------|--------------------------|
| `E_WEAK_MANDATE_BINDING` | `2001` | `high`/`critical` で `model_a_plus_b`（または派生証明・オンライン鮮度）を欠く場合、または `sensitive` で `model_c_offline_cache` を使用した場合 |
| `E_GRADE_INSUFFICIENT` | `2002` | セッショングレードが `grant.min_grade` 未満、または `FayingGrade × AccessMode × Criticality` マトリクスを満たさない場合 |
| `E_G0_EMERGENCY_OVERRIDE` | `2003` | `Human Prime` の `G0` 緊急引き継ぎが発動し、`Fay` 制御を拒否して非ブロッキング `safe_state_directive` を出力した場合 |
| `E_UNKNOWN_OPERATION` | `2004` | 要求された `resource_id` または `operation_id` が署名検証済み `DriverCapabilityManifest` に未宣言の場合 |
| `E_UNTRUSTED_MANIFEST` | `2005` | `DriverCapabilityManifest` の署名欠落、信頼アンカー不在、または Ed25519 署名検証失敗 |
| `E_CONFIRMATION_REQUIRED` | `2006` | `high`/`critical` 操作において有効期限内・端末開示証明付き・パラメータ SHA-256 一致の `HumanConfirmationProof` が欠落または不一致の場合 |
| `E_OUT_OF_SCOPE_FUND_TRANSFER` | `2007` | リクエストまたは操作が `domain_category == "fund_transfer"` を宣言し、CAP 1.0 の対象範囲外である場合 |
| `E_MANDATE_INVALID` | `2008` | Mandate の失効、期限切れ、オンラインモデルでの `online_fresh == false`、または主体・リソース・モードの不一致 |
| `E_PROTOCOL_VERSION_UNSUPPORTED` | `2098` | `protocol_version` がサポート対象の 2 セグメント文字列 `"1.0"` と一致しない場合 |
| `E_PROTOCOL` | `2099` | プロトコル構造エラーまたはフォールバックエラー。レガシー別名 `E_INVALID_MESSAGE` は入力正規化時に `E_PROTOCOL` へマッピングしなければならない（**MUST**） |

## 4.4 適合性（Conformance）判定基準

端末、ドライバホスト、またはランタイム実装が **CAP 1.0（`2025-10-25` 版次）** への適合を宣言するためには、以下の検証可能な全要件を同時に満たさなければならない（**MUST**）。

1. 第 0〜4 章に規定されたデフォルト拒否 8 段階評価パイプライン、単調重大度フロア、3 次元グレードマトリクス、パラメータ SHA-256 束縛型の `Human Prime` 確認ゲート、および `G0` 非ブロッキング安全状態指示を完全に実装すること
2. 入出力データ構造が `schemas/cap-1.0.cddl` および `schemas/cap-1.0.json` に厳密に準拠すること
3. 公式意味論的適合性テストベクタ集 `vectors/semantic/d1-d7-conformance.json` の全 14 件（`V01`–`V14`）を実行し、判定結果、実効重大度、ダウングレード抑制フラグ、エラーコード、診断コード、および安全状態指示が期待値と **100% 一致**すること
