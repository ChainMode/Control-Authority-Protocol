# 第 0 章：概要と規範的用語

## 0.1 プロトコルの目的と適用範囲

**制御権限プロトコル（Control Authority Protocol、CAP）** は、デジタルアバター（個人アバター `iFay` および公共ロールアバター `coFay` を総称する `Fay`）と、憑依（`Inhabit`）対象のホスト（`Host`、すなわち制御対象のハードウェア端末デバイスまたはクライアントアプリケーション）の間に位置する、デフォルト拒否（Default-Deny）型の制御権ゲートプロトコルである。CAP は上位の認可委任を個別のホストリソースおよびドライバ操作に対する決定論的なアクセス裁定へと変換し、不可逆的な物理動作や重要なシステム変更が実行される前に、暗号学的な能力下限と `Human Prime`（人間プライム）の意思による厳格な統制を保証する。

CAP 1.0 の規範的範囲は以下を含む。

1. 制御権評価リクエスト（`CapEvaluationRequest`）および決定論的裁定出力（`CapDecision`）のデータモデルとワイヤ形式
2. 暗号署名付きドライバ能力マニフェスト（`DriverCapabilityManifest`）の署名検証、重大度ベースライン、および不可逆性フロアの算出
3. `Faying-Protocol` の委任証憑（`MandateEvidence`）に対するオンライン鮮度検証およびセッション派生証明の検査
4. `FayingGrade × AccessMode × Criticality` の 3 次元認可判定マトリクス
5. 高リスク・致命的操作に対するパラメータ SHA-256 束縛型の明示的 `Human Prime` 確認ゲート（`HumanConfirmationProof`）
6. `Human Prime` による `G0` 緊急引き継ぎプリエンプションおよび非ブロッキング安全状態指示（`G0SafeStateDirective`）

**明示的な対象外範囲（Out-of-Scope）**：CAP 1.0 は ID 登録（詳細は `FayID` を参照）、推論意思決定（詳細は `Ego` を参照）、および社会貢献計測（`GMChain` 上の非金銭的単位 `MeriToken` の詳細は `Global-Merit-Chain` を参照）を扱わない。また、**金融決済や資金移動（`fund_transfer`）はプロトコル範囲外として厳格に排除**され、`domain_category == "fund_transfer"` を伴うすべての要求は無条件に拒否される。

## 0.2 RFC 2119 および RFC 8174 規範的用語マッピング宣言

本仕様書は IETF RFC 2119 および RFC 8174 の規範キーワード規約に準拠する。英語の大文字キーワード **MUST**、**MUST NOT**、**REQUIRED**、**SHALL**、**SHALL NOT**、**SHOULD**、**SHOULD NOT**、**RECOMMENDED**、**NOT RECOMMENDED**、**MAY**、**OPTIONAL**、または下表に定める日本語の規範表現が使用された場合、厳格な規範的効力を持つ。これら以外の通常の語法は規範的要件を構成しない。

| RFC 2119 / RFC 8174 英語キーワード | 日本語の規範的対応表現 | 規範的意味 |
|------------------------------------|------------------------|------------|
| **MUST** / **SHALL** / **REQUIRED** | **〜しなければならない** / **必須である** | 絶対的必須要件。1 つでも欠ける実装は CAP 1.0 適合を主張できない |
| **MUST NOT** / **SHALL NOT** | **〜してはならない** / **厳禁である** | 絶対的禁止事項。違反はプロトコル不適合および重大な安全違反となる |
| **SHOULD** / **RECOMMENDED** | **〜すべきである** / **推奨される** | 強く推奨される要件。安全影響を十分に評価し根拠を記録した場合にのみ逸脱し得る |
| **SHOULD NOT** / **NOT RECOMMENDED** | **〜すべきではない** / **推奨されない** | 強く回避すべき事項。逸脱には明示的なリスク評価を要する |
| **MAY** / **OPTIONAL** | **〜してもよい** / **任意である** | 純粋な任意機能。対向実装がその機能の有無を前提としてはならない |

## 0.3 主要規範用語

すべての実装ドキュメントおよびコードコメントは以下の用語規律に **MUST** 従わなければならない。

- **`Human Prime`（人間プライム）**：`iFay` の複製元であり、最終的な説明責任と最優先の引き継ぎ権を持つ自然人主体（正規識別子は `^hid_[a-z2-7]{16,}$` に一致する）。**自然人を指して「ホスト / Host」という語を使用してはならない（MUST NOT）。**
- **`Fay`（`iFay` / `coFay`）**：ホストリソースに対する制御リクエストを発行するデジタルアバター主体。
- **憑依（`Inhabit`）**：対象ホストへ `Fay` ランタイムを注入し、統制下で操作可能な状態にするプロセス。
- **ホスト（`Host`）**：`Fay` が憑依し CAP ゲートによって保護される**物理端末デバイス、アクチュエータ、またはクライアントソフトウェアアプリケーション**（機器・アプリのみを指し、人間を決して指さない）。
- **CAP 評価器（CAP Evaluator）**：ホストの信頼境界内に配置され、デフォルト拒否パイプラインに従って `CapEvaluationRequest → CapDecision` を決定論的に実行する規範コンポーネント。

## 0.4 直交する 3 つのバージョン軸と 2 セグメント `"1.0"` バージョン規律

CAP は互いに直交する 3 つのバージョン軸を採用する。実装はこれらを単一番号や 3 セグメント SemVer に統合してはならない（**MUST NOT**）。

1. **プロトコルバージョン（Protocol Version）**：ワイヤ形式に入る唯一の相互運用契約識別子であり、`PATCH` を持たない厳密な 2 セグメント `MAJOR.MINOR` 形式をとる。ワイヤヘッダでは `"CAP/1.0"` と表記し、`CapEvaluationRequest.protocol_version` および `protocol.version` フィールドでは 2 セグメント文字列 **`"1.0"`**（正規表現 `^(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$`）として固定される。
   - **MAJOR の増分**：既存のワイヤ形式またはデフォルト拒否不変条件を破壊する変更にのみ適用される。異なる `MAJOR` 間の互換性は保証されない。
   - **MINOR の増分**：後方互換性のある任意フィールドまたは列挙値の追加にのみ適用される。同一 `MAJOR` 内の高い `MINOR` 実装は `MAJOR.0` まで後方互換性を維持し（**MUST**）、未知の任意フィールドを無視しなければならない。
2. **文書ステータス（Document Status）**：フロントマターの `status` フィールド（大文字小文字を区別する `Draft`、`Final`、`Deprecated`、`Obsolete` のいずれか）にのみ記録され、ワイヤ形式やディレクトリ名に含めてはならない（**SHALL NOT**）。
3. **編集版次（Editorial Edition）**：公開日 `YYYY-MM-DD` で識別され（CAP 1.0 初回確定版次は **`2025-10-25`**）、ワイヤ形式や規範的意味を一切変更しない字句修正のみを担う。ワイヤ形式に含めてはならない（**SHALL NOT**）。

CAP 評価器がサポート対象外の `protocol_version`（例：`"2.0"` や 3 セグメント `"1.0.0"`）を受信した場合、推測によるダウングレードを行わず即座に拒否し（**MUST**）、`decision = "DENY"`、`effective_criticality = "critical"`、`error_code = "E_PROTOCOL_VERSION_UNSUPPORTED"`、および診断コード `2098` を返さなければならない。
