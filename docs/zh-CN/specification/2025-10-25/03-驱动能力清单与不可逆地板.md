# 第 3 章：驱动能力清单与不可逆地板

## 3.1 驱动能力清单（`DriverCapabilityManifest`）与密码学验签

操作危重度的底线 **SHALL NOT** 由发起调用的 `Fay` 或外部未受控输入决定，而 **MUST** 由宿主（`Host`）侧经可信公钥签名的 `DriverCapabilityManifest` 权威声明。清单包含以下核心字段：

- `manifest_id`、`driver_id`、`version`、`issued_at`：驱动清单唯一标识、版本号与签发时间戳；
- `signer_key_id`：指向宿主本地信任锚映射表（`TrustAnchorMap`）中的公钥条目标识；
- `resources`：非空的 `ResourceCapabilityDescriptor` 数组，声明每个 `resource_id`、可选的 `safe_states` 列表及非空的 `operations`（`OperationDescriptor`）列表；
- `signature_ed25519`：64 字节（128 个十六进制字符）的 RFC 8032 Ed25519 数字签名。

### 规范化验签流程

CAP 评估器 **MUST** 按以下步骤验证清单真实性：

1. 检查 `signature_ed25519` 是否为合法的 128 位十六进制字符串，并在 `trust_anchors` 中查找 `signer_key_id`；若缺失、算法不为 `"Ed25519"` 或公钥不为 64 位十六进制（32 字节原始公钥），立即判定验签失败。
2. 构造移除了 `signature_ed25519` 字段后的无签名清单对象，按 **RFC 8785 兼容确定性规范化 JSON**（所有对象键按 UTF-8 字典序升序排列、省略未定义可选字段、无多余空白符）序列化为 UTF-8 字节序列。
3. 使用信任锚的 Ed25519 公钥对该 UTF-8 字节序列执行标准 Ed25519 验签。

验签未通过时，评估器 **MUST** 立即返回 `decision = "DENY"`、`effective_criticality = "critical"`、`error_code = "E_UNTRUSTED_MANIFEST"` 与 `diagnostic_code = 2005`。

## 3.2 未知资源与未知操作默认致命拒绝

在已通过 Ed25519 验签的 `DriverCapabilityManifest` 中：

- 若找不到与 `req.resource_id` 精确匹配的资源描述符，或在匹配资源下找不到与 `req.operation_id` 精确匹配的操作描述符，CAP 评估器 **MUST** 将该次请求的 `effective_criticality` 强制设定为 `"critical"`，并立即返回 `decision = "DENY"`、`error_code = "E_UNKNOWN_OPERATION"` 与 `diagnostic_code = 2004`。
- 实现 **SHALL NOT** 为未在清单中声明的操作提供通配放行或默认降级为 `routine`。

## 3.3 后果不可逆性轴（`ConsequenceIrreversibility`）地板规则

为防止驱动编写者误将具有不可逆物理或数据破坏后果的操作标记为低危重度，每个 `OperationDescriptor` **MUST** 同时声明 `criticality` 与 `consequence_irreversibility` 两个字段。评估器 **MUST** 先按以下不可逆地板函数计算清单底线危重度 `floor_criticality`：

| `consequence_irreversibility` 取值 | 典型宿主操作示例 | 强制危重度地板规则 (`floor_criticality`) |
|-----------------------------------|-----------------|-----------------------------------------|
| `reversible` | 读取飞控姿态遥测、读取环境温度 | 保持 `operation.criticality` 不变 |
| `bounded_compensation` | 写入带自动回退的受界 PID 参数 | 保持 `operation.criticality` 不变 |
| `irreversible_consequence` | 解锁物理货舱门闩、发送外部物理信标 | $\max(\texttt{operation.criticality}, \texttt{high})$ —— 底线至少抬升至 **`high`** |
| `irreversible_data_or_hardware` | 不可恢复存储安全擦除、存在变砖风险的底层固件刷写 | **强制锁定为 `critical`**（无论 `operation.criticality` 原值如何） |

例如，即便某驱动将 `unlock_cargo_latch` 的基础 `criticality` 写为 `sensitive`，只要其声明了 `consequence_irreversibility = "irreversible_consequence"`，评估器计算出的 `floor_criticality` 即自动抬升为 `high`；同理，`flash_esc_firmware` 声明 `irreversible_data_or_hardware` 时，`floor_criticality` 强制锁定为 `critical`。

---

## 3.4 单调危重度上调与防降级夹紧（Escalation Clamping）

在获得 `floor_criticality` 后，CAP 允许上游委任凭据（`req.grant.criticality_override`）与当前调用方（`req.caller_criticality_override`）附加更严格的本地策略覆盖，但严格遵循**单调只升不降不变量**：

1. 令初始 `effective_criticality = floor_criticality`，初始 `escalation_clamped = false`。
2. 依次检查 `req.grant.criticality_override` 与 `req.caller_criticality_override`（若存在）：
   - 若某覆盖值严格低于 `floor_criticality`（即 $\text{rank}(\text{override}) < \text{rank}(\text{floor\_criticality})$），评估器 **MUST** 忽略该降级企图、保持不低于 `floor_criticality` 的等级，并将响应中的 **`escalation_clamped` 标记为 `true`** 以供安全审计记录；
   - 若某覆盖值大于或等于 `floor_criticality`，则更新 `effective_criticality = max(effective_criticality, override)`。

由此保证对任意请求恒成立：

$$\text{rank}(\texttt{effective\_criticality}) \ge \text{rank}(\texttt{floor\_criticality})$$
