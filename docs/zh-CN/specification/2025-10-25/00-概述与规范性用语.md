# 第 0 章：概述与规范性用语

## 0.1 协议使命与范围

**控制权限协议（Control Authority Protocol，CAP）** 是位于数字化身（`Fay`，含个人数字化身 `iFay` 与公共数字化身 `coFay`）与宿主（`Host`，即被附身控制的硬件终端设备或客户端应用）之间的默认拒绝（Default-Deny）控制权门控协议。CAP 将上游授权委任转化为针对具体宿主资源与驱动操作的确定性准入裁决，确保任何不可逆物理动作或关键系统变更在执行前受到密码学能力底线与人类原型（`Human Prime`）意愿的严格约束。

CAP 1.0 的规范范围覆盖：

1. 控制权评估请求（`CapEvaluationRequest`）与确定性裁决输出（`CapDecision`）的数据模型与线格式；
2. 经密码学签名的驱动能力清单（`DriverCapabilityManifest`）验签、危重度底线与不可逆后果地板计算；
3. 对上游 `Faying-Protocol` 委任证据（`MandateEvidence`）的在线新鲜度与会话派生绑定核验；
4. `FayingGrade × AccessMode × Criticality` 三维分级准入矩阵；
5. 高危与致命操作的参数哈希绑定人类原型显式确认门（`HumanConfirmationProof`）；
6. 人类原型 `G0` 紧急接管抢占与非阻塞安全态指令（`G0SafeStateDirective`）。

**明确排除的范围（Out-of-Scope）**：CAP 1.0 不负责身份注册（详见 `FayID`）、不负责推理决策（详见 `Ego`）、不承载社会贡献计量（公誉链 `GMChain` 上的非货币美誉值 `MeriToken` 详见 `Global-Merit-Chain`），且**严禁承载任何金融资金划转或支付清算指令**（所有 `domain_category == "fund_transfer"` 的请求一律拒绝）。

## 0.2 RFC 2119 与 RFC 8174 规范性用语映射声明

本规范遵循 IETF RFC 2119 与 RFC 8174 的规范性关键词约定。当英文全大写关键词 **MUST**、**MUST NOT**、**REQUIRED**、**SHALL**、**SHALL NOT**、**SHOULD**、**SHOULD NOT**、**RECOMMENDED**、**NOT RECOMMENDED**、**MAY**、**OPTIONAL** 出现，或下表所列中文规范性短语出现时，它们具有严格的规范性约束力；未按上述形式书写的日常用词不构成规范性要求：

| RFC 2119 / RFC 8174 英文关键词 | 中文规范性对应表述 | 规范性语义 |
|-------------------------------|-------------------|-----------|
| **MUST** / **SHALL** / **REQUIRED** | **必须** / **须** | 绝对强制要求；任一条不满足即不得声称符合 CAP 1.0 |
| **MUST NOT** / **SHALL NOT** | **不得** / **严禁** | 绝对禁止行为；任何违反均构成协议不一致与安全违规 |
| **SHOULD** / **RECOMMENDED** | **应当** / **建议** | 强烈建议遵循；仅在充分评估安全影响并记录理由时方可偏离 |
| **SHOULD NOT** / **NOT RECOMMENDED** | **不应** / **不建议** | 强烈建议避免；偏离前须完成显式风险评估 |
| **MAY** / **OPTIONAL** | **可以** / **可选** | 真正可选行为；各实现不得假定对端必定提供或必定省略该能力 |

## 0.3 核心规范术语

本规范严格遵循体系术语基线，任何实现文档与代码注释 **MUST** 保持一致：

- **人类原型（Human Prime）**：`iFay` 所复刻并对其行为享有最终控制权与最高接管权的自然人主体（规范标识符匹配 `^hid_[a-z2-7]{16,}$`）。**严禁使用「宿主 / Host」指代人类原型。**
- **Fay（`iFay` / `coFay`）**：发起宿主资源控制请求的数字化身主体。
- **附身（Inhabit）**：将 `Fay` 运行时注入目标宿主使其具备受控操作能力的过程。
- **宿主（Host）**：被 `Fay` 附身并受 CAP 门控保护的**物理终端设备、传感器执行器或软件应用实例**（仅指设备或软件，绝不指人）。
- **CAP 评估器（CAP Evaluator）**：部署在宿主可信边界内、按默认拒绝流水线执行 `CapEvaluationRequest → CapDecision` 判定的规范性执行组件。

## 0.4 三条正交版本轴与两段式 `"1.0"` 版本纪律

CAP 采用三条互相正交的版本轴，实现 **MUST NOT** 将它们合并为单一字符串或三段式 SemVer：

1. **协议版本（Protocol Version）**：唯一进入线格式的互操作契约标识，采用严格的两段式 `MAJOR.MINOR`（不设 `PATCH` 段）。在线信封头记为 `"CAP/1.0"`，在 `CapEvaluationRequest.protocol_version` 与 `protocol.version` 字段中固定编码为两段式字符串 **`"1.0"`**（匹配正则 `^(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$`）。
   - **MAJOR 递增**：仅用于破坏既有线格式或改变默认拒绝安全不变量的变更；跨 `MAJOR` 不保证兼容。
   - **MINOR 递增**：仅用于向后兼容的可选字段或枚举增补；同一 `MAJOR` 内高 `MINOR` 实现 **MUST** 兼容至 `MAJOR.0`，并忽略未知可选字段。
2. **文档状态（Document Status）**：仅记录于文档元数据 `status` 字段（取值为区分大小写的 `Draft`、`Final`、`Deprecated`、`Obsolete` 四者之一），**SHALL NOT** 进入线格式或目录路径。
3. **编辑版次（Editorial Edition）**：以发布日期 `YYYY-MM-DD` 命名（CAP 1.0 首发定稿版次为 **`2025-10-25`**），仅承载不改变任何线格式与规范性语义的纯文字修订，**SHALL NOT** 进入线格式。

当 CAP 评估器收到 `protocol_version` 不属于受支持协议版本（例如 CAP 1.0 评估器收到 `"2.0"` 或三段式 `"1.0.0"`）的请求时，**MUST** 立即拒绝并返回 `decision = "DENY"`、`effective_criticality = "critical"`、`error_code = "E_PROTOCOL_VERSION_UNSUPPORTED"` 及数值诊断码 `2098`，**SHALL NOT** 执行任何降级猜测。
