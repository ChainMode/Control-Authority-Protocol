# 第 4 章：高危人类原型确认与安全态

## 4.1 参数绑定的显式人类原型确认门（`HumanConfirmationProof`）

对于所有 `effective_criticality` 为 **`high`** 或 **`critical`** 的操作（**即使当前会话已处于最高信任等级 `G1`**），CAP 评估器 **MUST** 强制校验随请求提交的 `human_confirmation`（`HumanConfirmationProof`），绝不允许以「自动化便利」或「历史表现良好」为由免除逐次确认：

1. **规范身份校验**：`human_confirmation.human_prime_id` **MUST** 匹配规范化人类原型标识符正则 `^hid_[a-z2-7]{16,}$`。
2. **时效新鲜度校验**：`human_confirmation.expires_at_epoch_ms` **MUST** 严格大于当前评估时间戳 `req.now_epoch_ms`。
3. **宿主可信披露证明**：`human_confirmation.terminal_attested_disclosure` **MUST** 为 `true`，表明由宿主可信交互界面（而非 `Fay` 自报文本）向人类原型完整展示了目标资源、操作及不可逆风险。
4. **参数规范化 SHA-256 绑定**：计算本次请求 `req.params` 按字典序键排序规范化 JSON（见 §3.1）的 UTF-8 字节序列的 SHA-256 小写十六进制摘要（64 字符），`human_confirmation.confirmed_params_sha256` **MUST** 与该摘要逐字符完全相等。

若 `human_confirmation` 缺失，或上述四项条件中任一项不成立（例如确认后请求参数中的 `latch_id` 被篡改），评估器 **MUST** 立即返回 `decision = "DENY"`、`error_code = "E_CONFIRMATION_REQUIRED"` 与 `diagnostic_code = 2006`。

## 4.2 `G0` 人类原型紧急接管与零阻塞安全态指令

人类原型在任何时刻均享有对宿主的绝对优先接管权。当请求中携带 `g0_override == true` 或 `grant.mandate_binding.session_grade == "G0"` 时：

1. **立即抢占拒绝**：CAP 评估器 **MUST** 在 Mandate 过期/模式校验之前立即拦截 `Fay` 的控制请求，返回 `decision = "DENY"`、`error_code = "E_G0_EMERGENCY_OVERRIDE"` 与 `diagnostic_code = 2003`。
2. **确定性安全态指令（`G0SafeStateDirective`）**：
   - 若目标 `ResourceCapabilityDescriptor.safe_states` 非空，评估器 **MUST** 选择首选安全态 `safe_states[0].safe_state_id`，在裁决中输出：
     `{ "action": "enter_safe_state", "safe_state_id": "<safe_states[0].safe_state_id>", "blocks_human_takeover": false }`；
   - 若目标资源未声明 `safe_states`（或列表为空），评估器 **MUST** 输出：
     `{ "action": "terminate_and_alert", "blocks_human_takeover": false }`，指令宿主立即终止在途受控动作并向人类原型发出显式告警。
3. **零阻塞不变量**：在任何情况下，`safe_state_directive.blocks_human_takeover` **MUST** 恒为布尔常量 `false`。宿主的任何安全态过渡或清理流程 **SHALL NOT** 阻塞、锁定或延迟人类原型直接夺回物理或交互控制权。

## 4.3 规范错误码与数值诊断伴随码表

CAP 1.0 线格式采用稳定的大写下划线字符串作为规范错误码（`CapErrorCode`），并在测试向量与诊断日志中绑定一一对应的数值诊断码（`2001`–`2099`）：

| 规范错误码 (`error_code`) | 数值诊断码 (`diagnostic_code`) | 触发阶段与规范语义 |
|--------------------------|-------------------------------|-------------------|
| `E_WEAK_MANDATE_BINDING` | `2001` | `high`/`critical` 未使用 `model_a_plus_b`（或缺少派生证明/在线新鲜度），或 `sensitive` 使用了离线缓存 `model_c_offline_cache` |
| `E_GRADE_INSUFFICIENT` | `2002` | 会话等级低于 `grant.min_grade`，或不满足 `FayingGrade × AccessMode × Criticality` 矩阵 |
| `E_G0_EMERGENCY_OVERRIDE` | `2003` | 人类原型触发 `G0` 紧急接管，拒绝 `Fay` 控制并输出非阻塞 `safe_state_directive` |
| `E_UNKNOWN_OPERATION` | `2004` | 请求的 `resource_id` 或 `operation_id` 未在已验签 `DriverCapabilityManifest` 中声明 |
| `E_UNTRUSTED_MANIFEST` | `2005` | `DriverCapabilityManifest` 缺失签名、信任锚不存在或 Ed25519 验签失败 |
| `E_CONFIRMATION_REQUIRED` | `2006` | `high`/`critical` 操作缺失有效、未过期、终端证明披露且参数 SHA-256 匹配的 `HumanConfirmationProof` |
| `E_OUT_OF_SCOPE_FUND_TRANSFER` | `2007` | 请求或操作声明 `domain_category == "fund_transfer"`，超出 CAP 1.0 协议边界 |
| `E_MANDATE_INVALID` | `2008` | Mandate 已撤销、已过期、在线模型下 `online_fresh == false`，或主体/资源/模式不匹配 |
| `E_PROTOCOL_VERSION_UNSUPPORTED` | `2098` | `protocol_version` 不等于受支持的两段式版本 `"1.0"` |
| `E_PROTOCOL` | `2099` | 协议报文结构异常或兜底错误；历史别名 `E_INVALID_MESSAGE` 在输入归一化时 **MUST** 映射为 `E_PROTOCOL` |

## 4.4 实现符合性（Conformance）判据

任一终端、驱动宿主或运行时实现若声明符合 **CAP 1.0（`2025-10-25` 版次）**，**MUST** 同时满足以下全部可验证条件：

1. 完整实现第 0–4 章定义的默认拒绝 8 步评估流水线、单调危重度地板、三维分级矩阵、参数 SHA-256 人类原型确认门及 `G0` 非阻塞安全态指令；
2. 输入输出结构严格符合 `schemas/cap-1.0.cddl` 与 `schemas/cap-1.0.json`；
3. 加载并执行官方规范性语义测试向量集 `vectors/semantic/d1-d7-conformance.json` 中的全部 14 条测试向量（`V01`–`V14`），所有裁决结果、有效危重度、防降级夹紧标志、错误码、诊断码与安全态指令与预期值 **100% 一致**。
